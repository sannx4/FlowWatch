# Day 24 — Bulk snapshot ingestion, measurement validity, reproducibility

## Engineering question

Does PostgreSQL `COPY` into transaction-local staging followed by a single
set-based `INSERT ... ON CONFLICT` preserve the Day-23 canonical results, and
how does its latency compare with the existing row-by-row implementation?

The implementation follows the V5 Week-4 requirement: **bulk snapshots**, not
an unsupported claim that all entity ingestion has been vectorized. Region,
Country, Project and Credit still resolve using the Day-23 reference UPSERTs.

## Data contract and semantics

1. Dataset: versioned, **real World Bank offline JSON sample** supplied as
   `data/raw/world_bank_sample.json`; no invented rows contribute to throughput.
2. Input JSON SHA-256 is recorded; decimal literals are decoded with
   `json.loads(..., parse_float=Decimal)`. The file is not re-downloaded.
3. Canonical conversion and SQL numeric precision validation run before DML.
4. The canonical snapshot identity is `(credit_id, end_of_period)`, established
   by the existing unique constraint; the source credit number is used in the
   preflight duplicate check.
5. All exact financial, date, status, and source-lineage columns enter the
   `COPY` staging table. The surrogate PK/`created_at` are generated by PG.
6. Unchanged canonical snapshots are **not** updated: first accepted lineage
   remains. Changed rows default to **reject**; **ignore** leaves them intact;
   **update** requires explicit choice and a distinct source-record key.
7. Entity UPSERT behavior and update ordering match Day 23.
8. Caller owns the transaction. Failures must roll back *entity and snapshot*
   writes together. This initial test harness ALWAYS rolls back every trial.

The temporary stage is created using `CREATE TEMP TABLE ... AS SELECT ... WITH
NO DATA` rather than `LIKE`: it copies database column types without copying
PK/NOT NULL constraints on generated identity columns. `ON COMMIT DROP`
ensures session-local cleanup. `COPY` uses the psycopg3 connection checked out
by SQLAlchemy, inside the same transaction.

## Correctness evidence

`python -m scripts.day24_bulk_benchmark --sizes 5 25 50 100 --repeats 3`

For each batch and repetition:
- benchmark the Day-23 row loader and Day-24 COPY loader independently from
  the same PostgreSQL database state;
- transactionally roll back each method;
- compare *all* selected snapshot financial fields, exact calendar dates,
  source checksum, source key and ingestion run ID;
- compare the resolved parent region, country, project and credit attributes;
- assert identical entity/snapshot counts, unique temporal keys;
- preserve input order in both methods; alternate execution order to reduce
  measured warm-cache/order bias.

Additional rolled-back probes verify three bulk replays (only first inserts)
and identical **reject / ignore / update** semantics to the Day-23 reference.
A controlled correction is a test-only mutation, *not* observed World Bank
history and never committed.

## Experimental reporting

The benchmark report stores all raw timings (seconds), records per second,
per-path details, median end-to-end wall time and median reference/bulk ratio.
It reports slower outcomes rather than hiding them. No speedup target or
production throughput SLO has been pre-approved.

Actual performance depends on data size, existing parent rows, Windows Docker
I/O, local PostgreSQL, transaction and index overhead, disk cache, and driver.
`COPY` benefits may be small or negative at 5 records because parent resolution
is still row-oriented. A larger-scale evaluation belongs to later ingestion
and systems benchmark days.

## Research integrity and threats to validity

| Failure | Potential research distortion | Test/evidence |
|---|---|---|
| Lost snapshot during bulk merge | Missing credit-period targets, biased sample selection and maturity timing | Full key/row parity vs Day-23 + staged identity count |
| Duplicate credit-period rows | Inflated observation counts, falsely narrow uncertainty estimates | PK/unique constraint + three-replay probe |
| Decimal precision loss in COPY | Altered disbursement ratios and forecast residuals | Exact `Decimal` mapping + numeric scale gate + value parity |
| Incorrect status/date mapping | Look-ahead leakage or fabricated event ordering | Calendar/date/status parity |
| Rewritten lineage on identical replay | Cannot reconstruct source version for experimental results | Snapshot lineage parity + no-op update |
| Unreviewed correction overwrite | Retroactively edits historical evidence and invalidates point-in-time evaluation | Default reject + controlled correction probe |
| Timing only the fast portion | Misleading claims about practical ETL throughput | End-to-end wall times plus separately reported COPY/merge/entity timings |
| Source fixture does not trace to Mongo run ID | Misleading claim of operational lineage | Explicit *offline file fixture* identity, never counted as production ingestion |

## Scope limits / open decisions

- This is a single-writer isolated PostgreSQL benchmark. Concurrent source
  correction precedence/locking is not a proven guarantee.
- Day-24 benchmark reports file-backed source provenance, not MongoDB run
  provenance; it never persists fixture-specific artificial ingestion IDs.
- Distinct source observations remain **real**; the controlled correction is a
  rolled-back test case only.
- The benchmark proves parity for the specified bounded sample sizes, not the
  full history or all future World Bank source schema variants.
- The reference Day-23 implementation remains the correctness oracle.
- The original production loader and persisted `flowwatch` database remain
  unchanged. Production cutover awaits quality/quarantine and reconciliation.

This is a **systems-method validity result**, not the primary novelty claim for
maturity-aware cross-horizon conformal calibration.
